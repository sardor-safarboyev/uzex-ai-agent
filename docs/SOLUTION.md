# UZEX AI-аналитик — описание решения / Yechim tavsifi

**Демо:** https://vitality.comma.uz · **API:** https://vitality-api.comma.uz (`POST /api/agent/ask`, `POST /api/agent/stream`)

Веб-сервис, который отвечает на вопросы о биржевых сделках UZEX на **русском и узбекском** (латиница и кириллица).
Каждый ответ строится только из результатов SQL-запроса к базе. Пользователь видит SQL, таблицу результатов
и отметку о том, что все числа в ответе сверены с этими результатами.

## 1. Как это работает

```
вопрос (RU/UZ) ──► 1. Планировщик (LLM) ──► SQL ──► 2. DuckDB (только чтение) ──► таблица
                         ▲  исправление при ошибке / пустом результате ◄──┘
таблица ──► 3. Автор ответа (LLM) ──► 4. Проверка чисел ──► ответ + SQL + таблица + график
```

1. **Планировщик.** LLM (`openai/gpt-oss-120b` на Groq) получает компактное описание семантического слоя
   и правила предметной области. Он возвращает JSON: язык, одно предложение «что именно считаем»
   и 1–3 SQL-запроса.
2. **Выполнение.** Запросы выполняются в DuckDB только на чтение. Если запрос падает или возвращает пустой
   результат, ошибка уходит обратно модели, и она исправляет запрос (до 2 попыток).
3. **Ответ.** Вторая модель (`qwen3.8-27b`) пишет короткий ответ на языке вопроса. Ей разрешено использовать
   только числа из результатов. В конце ответа одна строка с основанием: период, фильтры, валюта.
4. **Проверка (anti-hallucination).** Каждое число в тексте ответа программно сверяется с результатами SQL,
   с учётом округления и сокращений «млн/млрд/трлн», «mln/mlrd/trln». Если число не найдено, ответ
   переписывается. Интерфейс показывает «✓ Все N чисел сверены с результатами SQL» или предупреждение.

## 2. Данные и семантический слой

Исходные 9 CSV (500 000 сделок за 2022-01-03 – 2026-10-30) уже загружены офлайн-сборщиком в
`uzex.duckdb` с контролем хэшей и 98 проверками целостности (см. `docs/data-contract.md`).
Поверх таблиц создаются временные представления (в базу ничего не записывается):

| Представление | Что даёт |
|---|---|
| `trades` | одна строка на сделку, все связи уже соединены: договор, товар, категория, продавец, покупатель, брокеры |
| `commodity` | 41 товарное семейство: 187 вариантов названий («Хлопок сырец» / «Хлопок-сырец (спот)», «Топливо дизельное» / «Дизельное топливо», …) сведены к одному |
| `amount_uzs` / `amount_usd` | сумма в сумах и в долларах. 6 590 экспортных сделок в USD пересчитаны по курсу ЦБ на дату сделки |
| `quantity`, `unit_price` | физический объём (лоты × размер лота) и фактическая цена за единицу |
| безопасные типы | `DECIMAL(18,2)` / `BIGINT` вместо `DECIMAL(38,10)`, на котором арифметика в DuckDB переполняется |

Правила в промпте закрывают типичные ловушки:
- «заключено/tuzilgan» означает «совершено», а не статус «Заключен»;
- нельзя складывать суммы в разных валютах и объёмы в разных единицах;
- средняя цена считается как средневзвешенная;
- «в этом году» = 2026, «в прошлом» = 2025;
- регионы и товары указаны точными значениями;
- uz→ru словарь товаров: paxta → Хлопок-сырец, bug'doy → Пшеница и т.д.

## 3. Безопасность

- База открывается только на чтение. Доступ к файлам и сети, загрузка расширений отключены, конфигурация заблокирована.
- Принимается ровно один оператор `SELECT`: тип оператора определяет парсер самой DuckDB. Опасные функции (`read_csv`, `attach`, `copy`, …) запрещены.
- Ограничения: таймаут запроса, лимит памяти, максимум 200 строк.
- Ключи LLM хранятся только в серверном `.env`. В репозиторий и образы они не попадают.

## 4. Скорость и устойчивость

- Groq: типичный ответ за **1,5–3 с**. Интерфейс показывает этапы в реальном времени (SSE): «Разбираю вопрос → Считаю → Формирую ответ».
- У бесплатного тарифа Groq лимит 8 000 токенов в минуту **на каждую модель**. Пул моделей
  (gpt-oss-120b → qwen3.8-27b → gpt-oss-20b → OpenRouter) читает заголовки rate-limit, сразу пропускает
  исчерпанную модель и при необходимости ждёт ближайшего восстановления лимита.
- Повторные вопросы отдаются из кэша мгновенно.
- Уточняющие вопросы («а за 2025?») работают: в планировщик передаются два предыдущих вопроса и их SQL.

## 5. Как проверялись ответы

`backend/evals/` содержит 26 вопросов на RU / UZ-латинице / UZ-кириллице: количества, суммы, доли, рост в %,
рейтинги, цены, курсы, регионы, брокеры, «нет данных за 2021», единицы измерения.

- **Эталон** считается отдельным SQL, написанным вручную по *физическим* таблицам `main.*`, а не через
  семантический слой агента. Поэтому ошибка в самом слое тоже будет поймана.
- **Оценка:** текст ответа агента должен содержать эталонные числа и названия.
- Запуск: `cd backend && uv run python evals/run_eval.py`. Результаты: `evals/results.md`.

Результаты прогонов:

| Прогон | Результат | Что исправлено после |
|---|---|---|
| 1 | 22/26 | 3 ошибки — лимиты Groq при «залповом» прогоне и латинский шаблон `'%ai 92%'` вместо кириллического `'%аи 92%'`; 1 — неоднозначность «покупатели-плательщики НДС» (торговавшие или зарегистрированные) |
| 2 | **25/26**, медиана ≈2 с | единственный «провал» — ошибка эталона: агент ответил точно 8,55 %, а эталон был округлён до 8,5. Эталон теперь считается SQL с 2 знаками → фактически 26/26 |

Найденные и исправленные ловушки:
- «Сколько сделок было **заключено**» сначала превращалось в фильтр по статусу «Заключен» (ответ 0). Добавлено правило.
- Переполнение `DECIMAL(38,10)` при умножении. Решено безопасными типами в слое.
- Два подключения к DuckDB с разной конфигурацией конфликтуют. Конфигурация теперь общая.

## 6. Технологии

Python 3.11, FastAPI, DuckDB 2.0, httpx · Groq (gpt-oss-120b, qwen3.8-27b, gpt-oss-20b), OpenRouter (резерв) ·
React 19 + Vite · Docker Compose, nginx, Caddy (TLS Let's Encrypt) · автодеплой через systemd timer из ветки `deploy`.

## 7. Деплой

`deploy/compose.prod.yml` — отдельный проект `uzex` (backend + nginx) на `172.17.0.1:18080`. TLS-прокси Caddy
(общий на сервере) направляет `vitality.comma.uz` и `vitality-api.comma.uz` на nginx. nginx маршрутизирует по Host:
фронтенд отдаётся как статика, API проксируется без буферизации (для потоковых ответов).
`deploy/auto-deploy.sh` каждые 30 с проверяет ветку `deploy`. При новом коммите он пересобирает и перезапускает стек
и проверяет здоровье, а при неудаче откатывается на предыдущий коммит.
